# Verifying changes in swe-verify

Generated by `swe-verify skill` from this project's config, committed plans and installed
adapters. Do not edit — re-run the command and it will describe the project as it is now.

Every step is a command. Pass `--json` and read the JSON; never parse prose.

## 1. Pick the plan

Pass the id of the plan whose scope covers the files you changed:

- **`fixture-go-pricing`** — the Go tiered discount fixture returns a discounted total for a tier-2 customer
  - covers `fixtures/l1/go/**` — 1 assertion(s)
- **`fixture-pricing`** — the tiered discount fixture computes a discounted total for a tier-2 customer
  - covers `fixtures/l1/py/**` — **no assertions**: it proves the code ran, not that it behaved. Add one before relying on it.

If nothing covers what you changed, the gate reports `SV012`. Write a plan rather than widening an
existing one past what it claims to prove, then commit it with the change — a reviewer reads what
you set out to prove before they look at whether it went green:

```bash
swe-verify plan --intent "<what this change proves>" --scope "<glob>" --json
```

## 2. Prove it, and film it

```bash
swe-verify verify --plan <plan-id> --record --json
```

One command: instruments every changed line, brings the fixture up, drives the plan, evaluates
the gate. `--record` adds a captioned MP4 to `story.artifacts`.

**`--record` needs the plan to say what to film.** Steps with `"driver": "web"` film themselves —
the page is the evidence. A change with no screen has to name the commands worth watching, in a
`record` block:

```json
"record": {
  "terminal": {
    "steps": [
      { "caption": "BEFORE — the test fails on a cancelled context",
        "command": "go test ./pkg/... -run TestThing", "waitMs": 30000 },
      { "caption": "the one-line fix", "command": "git diff -U1" }
    ]
  }
}
```

Each beat becomes its own clip with its caption rendered as a **card spliced in front of it** —
never typed into the shell, where a `# comment` would be indistinguishable from the program's
own output. Each beat is a fresh shell, so beats must be independent commands.

A plan that declares nothing filmable exits `3`: recording was asked for and there was nothing to
record, and a green verdict with no film is what recording exists to prevent.

| Exit | Meaning | Next move |
|---|---|---|
| `0` | allow | go to step 3 |
| `2` | block | act on each finding's `remedy` — never weaken the plan |
| `3` | usage or config error | fix the plan or config |
| `4` | **harness failure** | swe-verify could not observe. Not your change's fault; run `swe-verify doctor` and report it |
| `5` | bypassed | recorded and amber, never green |

## 3. Film the reproduction too

A recording of the working state proves nothing on its own — a reader cannot tell a fix from a
film of a healthy system. What convinces is the pair.

```bash
git stash                                        # or: git checkout <base>
swe-verify run --plan <plan-id> --record --json  # the bug, reproduced
git stash pop
```

Which recording you get is decided by **what is checked out** — the tool does not revert files
for you, because a revert that dies mid-run leaves a wrecked working tree. Each file names its
own branch and commit, and is marked `-dirty` when the tree had uncommitted changes.

**Checking out the base is wrong when the fix and its test landed together.** Reverting the
commit reverts the strengthened assertion too, so the old weak test passes against the old buggy
code and the recording shows green — a reproduction that reproduces nothing. Revert only the
production line instead, and keep the test that detects the bug:

```bash
git checkout HEAD~1 -- <the-source-file>          # not the test
swe-verify run --plan <plan-id> --record --json
git checkout HEAD -- <the-source-file>            # put it back
```

Then read the transcript before you attach anything. If the "before" run passed, you filmed a
healthy system and have no reproduction.

A reproduction **must not end on the working state**: the same plan runs against both builds, so
a reconciling final beat makes the pair indistinguishable at the frame a reviewer scrubs to.

## 4. Collect the artefacts

```bash
swe-verify show --run <run-id> --json
```

```
.swe-verify/runs/<run-id>/
  story.json                 the sealed evidence
  artifacts/video/run.mp4    the recording          readableBy: [human]
  artifacts/…                what the agent reads   readableBy: [agent]
  logs/harness.log           what the harness did
  viewer.html                30-second audit, offline
```

## 5. Open the PR

```bash
gh repo fork <owner>/<repo> --clone=false   # once, if you do not own the repo
git remote add fork https://github.com/<you>/<repo>.git
git push -u fork <branch>
gh pr create --repo <you>/<repo> --base <the fork's default branch> --head <branch> \
  --title "<title>" --body-file body.md
```

Target **the fork's own default branch**, not the upstream project's — check it with
`gh repo view <you>/<repo> --json defaultBranchRef`, since it is `master` on older repositories.
`--remote=false` is rejected when a repository argument is given, so add the remote yourself.

Put a placeholder where each recording goes (`BEFORE_VIDEO`, `AFTER_VIDEO`). State what the
evidence shows — and if the pair shows no difference, say that rather than implying one.

## 6. Attach the recordings — needs a logged-in browser

**`gh` and a token cannot reach GitHub's `user-attachments` CDN**, so there is no CLI path for
this. A body referencing a local path renders nothing.

1. Open the PR in a browser already signed in to GitHub
   (`document.querySelector('meta[name="user-login"]')?.content` to confirm).
2. Upload each file into the **"Paste, drop, or click to add files"** control.
3. Wait for `https://github.com/user-attachments/assets/…` to appear, one per file.
4. **Clear the box** so no stray comment posts.
5. Substitute the URLs into the body and publish:

```bash
gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@body.md
```

## 7. Verify the evidence is really there

Not in a browser. `video.readyState` reports `0` on perfectly good attachments whenever the
page is busy — two agents chased that false failure and nearly reported working evidence as
broken. Ask whether the URL resolves to media bytes instead:

```bash
for id in $(gh pr view <n> --repo <owner>/<repo> --json body -q .body \
    | grep -o 'user-attachments/assets/[0-9a-f-]*' | cut -d/ -f3 | sort -u); do
  loc=$(curl -sI -H "Authorization: token $(gh auth token)" \
        "https://github.com/user-attachments/assets/$id" | tr -d '\r' | sed -n 's/^[Ll]ocation: //p')
  curl -sI "$loc" | grep -iE '^(HTTP|content-type|content-length)'
done
```

`video/mp4` and a plausible size is evidence. `text/html` means the link resolves to a page,
not a file. No output at all means the body still has its placeholders in it.

## Findings you will meet

| Code | Merge | What happened | What to do |
|---|---|---|---|
| `SV001` | blocks | no story for this change — nothing was run | Run the verify command below and keep the story it produces. |
| `SV003` | blocks | stale evidence — the code changed after the story was sealed | Run verify again against the current head. |
| `SV004` | blocks | the story ran a different plan than the one committed in the tree | Commit the plan the story executed, or re-run against the committed one. |
| `SV010` | blocks | a changed line was never executed | Add a step that reaches the line, or waive it with a dated reason. |
| `SV011` | blocks | a probe was accepted but never verified — the line was never watched | Run `swe-verify doctor` — this is a path-mapping problem, not a coverage one. |
| `SV012` | blocks | a changed file is not covered by any plan scope | Add the file to a plan's scope.include, or exclude it in config if it is not gateable. |
| `SV013` | blocks | a coverage waiver expired, or is about to | Exercise the line, or renew the waiver with a reason that still holds. |
| `SV014` | policy | a defensive line was never exercised | Provoke the failure path, or leave it — under the default policy this only warns. |
| `SV015` | blocks | waivers cover more of the diff than the configured cap allows | Exercise some of the waived lines instead of waiving more. |
| `SV016` | warns | changed code in a language with no trustworthy debug adapter, so it was not gated | Nothing to do: that language has no adapter here, so it is not gated. |
| `SV020` | blocks | an assertion failed | Fix the behaviour, or correct the assertion if the expectation was wrong. |
| `SV021` | warns | the plan has no assertions, so a green run proves execution but not behaviour | Add an assertion, so a green run means something. |

## What this project can gate

Instrumentable here: **py** (debugpy), **go** (delve).

Not instrumentable here — changes in these languages are reported as ungated (`SV016`) rather than silently passed:
- **ts** (js-debug): js-debug (the DAP server for Node/TypeScript) is not vendored in this build → Point SWE_VERIFY_JS_DEBUG at a dapDebugServer.js. Node's own --inspect speaks CDP, not DAP, so it cannot be used directly.
- **java** (java-debug): java-debug (com.microsoft.java.debug.plugin) is not vendored in this build → Point SWE_VERIFY_JAVA_DEBUG at a java-debug plugin jar.

Drivers: `api` (HTTP), `web` (Playwright is installed).
Gate scope: `fixtures/**`, excluding `**/*.md`, `**/*.test.*`, `**/dist/**`, `**/node_modules/**`.

## Policy here

- Defensive lines (catch blocks, guards, throws): **warn** — unexercised ones warn, they do not block.
- Waivers may cover at most **10%** of a diff before the gate refuses them.
- A bypass needs a reason and is published: apply the `swe-verify:bypass` label and put
  `swe-verify:bypass: <reason>` in the change description, or pass `--bypass "<reason>"` locally.
- A run has 10 minute(s) and at most 500 probes.

## Rules

Each one comes from a recording that misled somebody.

- **A run that records nothing fails.** A green result with no video is the failure recording exists to prevent.
- **A caption narrates what the frame renders.** A value that was measured and which the app does not
  draw belongs in the probe dock, headed `MEASURED`.
- **Narration is never typed into the app or the shell.** Title cards are spliced in; the terminal
  shows commands and their output, nothing else.
- **Never narrow a plan's scope, delete its assertions, or waive a line to turn the gate green.**
  Those are the only tools that make a pass mean anything.
- **Do not bank a vacuous claim.** If a precondition was absent, or the pair shows no difference,
  say so on screen and in the PR.
- The same gate runs in **CI** whether or not you run it here. Running it locally is how you find
  out before review, not a way around it.

## What the tooling cannot do here

- `docker compose down` has no `--rmi`, so a `build: true` fixture leaves one image per run.
- Attaching video to a PR (step 6) has no CLI path.
- Each filmed beat is a fresh shell, so a beat cannot depend on state a previous one set up.
- No adapter for **ts**, **java**: changed lines there are
  reported as ungated (`SV016`) rather than silently passed.
